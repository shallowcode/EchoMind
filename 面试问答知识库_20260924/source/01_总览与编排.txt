B02|P0|代码已核对|上下文隔离,职责污染,scope_message|scope,run|D01,E03
上下文隔离是提示词说“别管别的”，还是实际裁剪？
两者都有。技术任务先把原消息按分句切开，仅保留技术片段，并移除订单实体；其上下文只保留画像和相关用户技术历史，随后再加职责提示与工具白名单。

隔离是降低串扰，不是隔离进程、容器或完整信息流安全证明。

B03|P1|代码已核对|并发,asyncio,gather,ContextVar|run,shared|F04,I01
多个任务怎么并发，状态为什么不会相互覆盖？
_run使用asyncio.gather执行各Subtask，并用ContextVar绑定当前请求和任务。每个任务拥有自己的状态对象；请求内shared和locks字典有意共享，供相同工具结果复用。
local是请求上下文的浅复制，因此不能笼统说所有数据都被深复制隔离。代码依靠独立task对象、任务局部绑定、共享结果锁和明确读写约定维持边界。
asyncio并发就等于多个CPU核并行吗？
不等于。主要收益是重叠模型和存储I/O等待；同步阻塞操作用to_thread移到工作线程。CPU密集任务是否能并行还取决于实现和运行时。
当前任务队列没有通用DAG依赖求解，也没有跨进程共享的请求级锁。

B05|P0|代码已核对|有限重试,补做,预算|agent,settings|B06,I02
“有限重试与补做”怎么限制，最多多少轮？
通用ToolAgent循环上限是max_tool_rounds+1；默认3轮工具机会，最后一轮只允许回答。格式修复、缺项补做也消耗这个循环预算，而不是各自无限重试。
一次结构化输出最多3个工具调用；循环中的工具按顺序执行，子任务之间并发。当前确定性订单和退款处理分支不按这个通用模型循环计数。
三轮工具意味着一次请求最多调用三次模型吗？
不是。意图识别、摘要、RAG改写和重排也可能调用模型，多任务又分别有循环。总模型调用量应从trace统计，不能用工具轮数代替总成本。
预算是次数约束；还需请求总超时和资源限制，不能保证复杂请求必然完成。

B06|P1|代码已核对|重复调用,seen,重试限制|agent,shared|E10,B05
模型反复输出同一个工具调用怎么办？
通用Agent用工具名和排序后的参数构造signature，已出现的调用会返回“使用前次结果”的提示。请求级成功结果还会共享，避免不同任务重复做同一操作。
细节是seen在真正执行前就加入，因此同一个Agent中完全相同参数的失败调用也可能被挡住。缺项补做不等于对所有瞬时失败自动执行原参数重试。
这个策略有什么不足，怎么改？
可把调用记录区分成功、确定性拒绝和可重试失败；只对可重试读操作做有界退避，写操作先查询幂等结果。该改法需新增测试，不能假定当前已实现。
不要把当前循环描述成具备完善指数退避、错误分类和自动恢复的重试框架。

B07|P0|代码已核对|结果共享,去重,锁|shared,tools|F01,E11
两个 Agent 都查同一个订单，怎么只执行一次？
请求内以工具名和规范化参数构造key，为key建立asyncio.Lock；拿锁后先查shared，成功执行后保存结果。第二个任务在锁内看到已有结果后复用，并在trace标记shared。
仅先查字典不加锁会出现两个任务同时miss；锁后的二次判断才避免并发重复。这是请求级共享，身份由当前请求统一确定。
请求级共享能保证用户刷新后不会重复退款吗？
不能，刷新是另一个请求，内存共享已消失。跨请求和进程重启依赖数据库唯一约束、业务幂等键及请求响应重放。
不要把请求内去重、知识缓存和业务幂等说成同一个机制。

这样牺牲一些自然的整体行文，换来可见的任务覆盖。前置任务仍要验证自身内容，否则只会把错误完整地拼出来。

确定性拼接解决遗漏风险，不等于已经消除所有事实冲突。

B09|P0|代码已核对|partial,degraded,awaiting_input,denied|gaps,run|E07,H04
partial、degraded、awaiting_input 和 denied 分别是什么意思？
partial表示有子任务未完成；degraded表示请求可能形成结果，但模型、缓存或投影等出现降级；awaiting_input表示缺必要信息；denied表示业务规则确认拒绝，不是服务宕机。
例如超过可退余额是确定性业务拒绝，缺订单号是待补充，知识库不可用而订单查到是部分完成。顶层状态按任务和trace综合得出，不能只看HTTP 200。
合法拒绝在评测里算成功还是失败？
由任务目标决定。越权或超额场景期望安全拒绝时可以判完成；普通退款本该成功却被拒绝，不能因为没有事故就记成功。
当前denied识别有具体业务码与答复规则，不能泛化为所有拒绝都自动正确分类。

B10|P1|代码已核对|异常隔离,gather,降级|run,render|J04,I01
一个 Agent 报错，其他 Agent 会一起失败吗？
任务执行函数内部捕获普通Exception，把当前任务标成blocked并保留失败原因；因此单项常见异常不必让其他项失去结果。最终逐项渲染并返回partial。
请求总超时和取消属于更高层边界，不能与普通子任务异常混为一谈。若外层取消gather，多个未完成任务都可能被取消。
为什么不让通用 Agent 接管所有失败？
无差别接管可能让不具备工具权限或上下文的角色生成貌似成功的答案。当前保持任务归属，比静默变成通用闲聊更容易审计。
这不是完整的故障容错调度系统；已发生业务写入仍需单独核验。

B11|P1|设计推演|任务依赖,DAG,并发顺序|run,refundstore|F02,J02
订单查询和退款有先后依赖，为什么可以并发？
任务层面可以并发，但退款本身在业务事务里重新核验订单和可退额度，不依赖另一个Agent口头传来的订单结论。需要保证的是写操作内部前置条件成立。
如果需求是“先修改订单，再按新订单退款”，当前全部gather不能表达这个依赖。应新增depends_on、只读与写入分类、拓扑执行，以及失败传播策略。
并发查询可能读到退款创建前的状态吗？
可能。请求内共享读结果也可能相对后续写入过时。涉及同一资源的读后写展示，应明确读时点或在写后重新读取；当前不能宣称请求级快照一致。
通用DAG和写后缓存失效是建议，不是现有完成能力。

角色工具过滤只影响提示词，还是执行也会检查？
提示词只展示角色与子任务允许的工具，执行层也检查task.allowed_tools和角色capabilities，然后工具服务再做参数与业务权限校验。模型自己输出一个未展示工具名不能直接绕过限制。
能力限制回答“该角色能做什么”，Principal和对象归属回答“这个登录身份能操作谁的数据”。两层约束针对不同问题。
为什么不能只靠工具不写进prompt？
模型仍可能猜到工具名称或受外部文本诱导。服务端必须拒绝未授权调用；隐藏工具只是减少误调用概率，不能作为安全措施的全部。
Agent角色与真实用户角色不能混用；billing并不自动赋予finance审批权。

“退500元”会不会被误拆成HTTP 500故障？
当前技术规则要求错误码伴随HTTP、接口、报错等上下文，或带明确错误词，并避免把紧跟“元”的数字当错误码。测试包含退款金额不是HTTP错误的用例。
这是典型的实体与意图冲突：同样的数字在金额、订单号、状态码里语义不同。应先识别上下文，再决定是否创建技术子任务。
正则越来越多时该怎么办？
整理出结构化槽位与反例集，用规则处理高风险确定性边界，必要时让模型输出候选结构再校验；按业务域维护而不是无序叠加表达式。
规则测试证明覆盖已列举用例，不能证明所有中文表达都正确。
