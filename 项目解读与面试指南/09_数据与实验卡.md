## 实验设计与可复现条件

每个任务分别在 single 和 multi 下执行。双方使用相同模型和版本化知识、相同权限与业务工具、相同工具预算。single 使用全工具通用 Agent + 单查询召回；multi 使用原路由、角色 SOP、可并行协作及查询增强。任务顺序固定随机打乱，配对内先后顺序交替。

每个任务/方案独立 SQLite 数据库、独立 tenant，避免退款、记忆与缓存跨组污染。向量目录可共享，但所有写入、召回都带独立租户范围；工具缓存每个应用实例重新建立。模型预热一次并剔除，但操作系统文件缓存、模型服务上下文缓存和桌面负载没有完全隔离，不能称为严格专用性能实验室。

记录模型名、GGUF 文件与 llama.cpp 压缩包 SHA256、关键依赖版本、Python 版本、数据集 SHA256、参评源码 SHA256、模型预算、并发数与检索后端。运行中参评源码发生变化会被报告标记。最终报告还应与相应逐例 JSON 一起保存，而不是只保留一个“提升百分比”。

模型来源：[Qwen3-1.7B-GGUF 官方卡](https://huggingface.co/Qwen/Qwen3-1.7B-GGUF)，revision `90862c4b9d2787eaed51d12237eafdfe7c5f6077`；本地文件 SHA256 `061b54daade076b5d3362dac252678d17da8c68f07560be70818cace6590cb1a`。使用 CPU llama.cpp、2 个推理槽位、总上下文 16384、6 个线程。两个推理槽位不是“同时服务 2 个业务任务”的保证，一个复合业务任务本身也会发出多个模型调用。

## 指标口径

- **任务完成率：** 每个方案以全部 24 条任务为分母，不能删除失败、超时或不支持的案例。工具名与真实结果、数据库退款金额/状态、工单闭环都是检查项；后来增加虚假到账声明检查，以及 401 任务的检索/答复依据检查。
- **复合任务完成率：** 只取 8 条 compound，不能用全部任务完成率替代它。
- **HTTP 请求 P95：** 以每条客户消息的完整 HTTP 耗时取 nearest-rank 第 95 百分位。测量包括模型 HTTP 调用、身份检查、SQL 读写与服务处理，不含公网或反向代理。
- **任务耗时：** 包括该任务的所有客户轮次和模拟人工 HTTP 操作。评委调用放在任务计时之外；人工是脚本模拟接单，不代表真实人工等待时长。
- **模型 API 费用：** 当前本地模型不调用外部付费生成服务，单价设为 0；机器折旧、电费、运维、评委调用等不能由这个 0 推导出来。没有价格或 usage 时报告 null。
- **四维 Judge：** relevance/accuracy/completeness/helpfulness，严格限制在 0–1，失败单列。相同小模型评价自己有偏差，不能把平均 Judge 分数当成独立正确率。
- **置信区间：** 完成率给 Wilson 95% 区间，方案差给配对 bootstrap 区间。固定小集的区间仍不能代表真实线上所有用户。
- **退化检测：** 相同条件报告间比较相对下降/上升 5%；它是工程告警门槛，不是显著性检验。

## 如何处理不理想的结果

首次 24 条全量运行：single 12/24，multi 8/24；两组 compound 都是 0/8。它没有支持“多 Agent 提升完成率”的结论。可解释为当前组合方案与小模型的规划、工具选择、角色分工存在瓶颈；不能只凭这个实验将问题归咎于某一个组件。

首次外部意图评估：48 条映射样本准确率 23/48（47.92%），macro-F1 0.5247。该结果是固定英文样本、当前映射与本地模型的观测，不是全部 19 类中文意图的质量指标。

如果后续换更强模型，保持数据与口径，分别比较“同方案换模型”和“同模型换方案”。若增加用例或修改判定标准，应升级数据/验证版本，不能把不兼容报告拼成从 A 提升到 B。

历史 Qwen 阶段适合写入简历的是：“建立包含事务状态核验、真实 HTTP 链路、工具 trace、延迟与 token 成本的可复现评测体系，使用固定业务回归集和独立报告的公开意图样本识别模型与编排瓶颈。”当前已取得 GLM 对照数据，可以使用本章开头及实测汇总中的数字，同时保留样本与实验条件。
