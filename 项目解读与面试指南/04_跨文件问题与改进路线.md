# 跨文件核实：实现、缺口与下一步

输入：实际源码、部署配置、已有材料及隔离复现。输出：有证据、可排序、可验收的改进清单。以下是审阅结论，未修改业务源码；严重度按功能正确性、数据一致性和后续上线影响安排，不代表本次做了完整安全审计。

## 先纠正容易讲过头的能力

| 原设计/材料表述 | 当前真实实现与证据 | 面试应怎样说 |
|---|---|---|
| MCP 工具框架 | tool_manager 的注册表 + 本地 handler；没有协议端点/会话 | 有 MCP 风格工具可靠性封装，未接协议 |
| 人工升级 | orchestrator L332–338 标记/日志；池无 escalation 实例 | 预留升级信号，尚无工单闭环 |
| 回答置信度低就升级 | AgentResponse.confidence 默认1，未赋质量分 | 用关键词/意图/紧急度判升级 |
| 多 Agent 自动协商 | gather 后字符串拼接 | 规则驱动的主辅并行回答 |
| Embedding 全由 Anthropic 生成 | intent 本地哈希或条件远端；知识/记忆传 Chroma 文本接口 | 区分意图词面向量与 Chroma embedding |
| LRU 意图缓存 | dict 插入顺序批量淘汰，没有访问更新 | 有有界结果缓存，非严格 LRU |
| 三级记忆按时效/重要性融合 | 固定顺序拼接，历史检索按库结果 | 分层存储与上下文组装，未做综合排序 |
| 端到端评测全链路 | evaluator 调用 Orchestrator，未走 chat | 编排器级对话评测，服务级评测待补 |
| Java/Spring 实现 | 当前无 Java 工程 | 本仓库是 Python/FastAPI |
| SOC2/准确率92%/召回提升40% | 演示材料的文字，无匹配实验/认证证据 | 不作为事实引用 |

## 第一批：修复能明确复现的正确性问题

| 问题与证据 | 触发与影响 | 建议修改 | 验收方法 |
|---|---|---|---|
| 记忆压缩倒序，memory L280–294 | 15条触发压缩，5条保留区读出倒序 | 统一 Redis 新→旧契约，按 keep 原序 LPUSH 或统一批量写顺序 | 输入1..15，压缩后读取11..15；再追加16，顺序仍连续 |
| 压缩非原子，memory L249–285 | LLM等待期间新消息被后续delete删掉 | 会话级锁/版本CAS，原子截断已归档区，先确保存档成功 | 并发追加和压缩，所有消息恰好一次且顺序正确 |
| 入口实体丢失，orc L303–306 | CLI/评测内部识别不写回entities | 补实体，或统一ChatService前置处理 | 同输入经HTTP/CLI/评测得到相同实体与路由 |
| 去重含score，tools L341 | 同chunk不同查询距离不同，占满Top-K | 存储返回稳定chunk_id，按ID去重，合并证据 | 同ID不同score只保留一条，不同ID不能误合并 |
| 半开全部放行，tools L87–95 | 冷却后并发探测压坏恢复依赖 | HALF_OPEN最多一个/有限探测令牌，清楚处理取消 | 同时10次allow最多1次探测；成功后恢复正常 |
| Webhook Enum JSON，monitor L301 | 配置webhook触发阈值，序列化失败 | severity.value显式转换，检查响应状态 | 假HTTP服务收到合法JSON；错误状态记录可重试失败 |
| Compose缺Chroma覆盖，yml L81–86 | .env示例localhost进入应用容器 | 显式CHROMA_HOST=chromadb、PORT=8000 | 集成启动时报告server模式，导入结果可从独立服务读到 |

**为什么先做这批：** 每项都能从明确输入推导不正确状态，不需要先采购模型或换框架。数据顺序和执行状态不可靠时，换更强模型也无法补救。

## 第二批：使“成功”和“质量”可观察

| 缺口 | 跨模块后果 | 下一步与验收 |
|---|---|---|
| fallback也success=True，API设knowledge_used | 用户以为引用知识，实际只有故障说明 | 增加status/degraded/retrieval_success，并返回来源ID；故障时不标真实知识命中 |
| reranked固定True | 看不出重排跳过/失败 | 区分attempted/applied/fallback；用解析失败与候选≤k验证 |
| 编排latency当chat总延迟 | 忽略记忆、识别、RAG和写入 | HTTP入口计时+每阶段span；分段总和与总延迟基本一致 |
| 成功率只指LLM不抛异常 | 空答案/幻觉也算成功 | transport_success、task_success、groundedness分开；增加可核验任务结果 |
| Histogram采累计均值且Counter不增 | P95与请求数不可信 | 请求完成时observe实际秒/毫秒并用正确桶；每HTTP请求计数一次 |
| 告警不解决、不去重、无上限 | 常态故障造成重复通知和内存增长 | 告警状态机、冷却、恢复通知、保留上限；持续故障只发策略允许次数 |

Monitor 的降权反馈本身已经连接，但应先修统计口径，再增加同类实例和恢复探索。否则只是对不可靠数字做更复杂决策。

## 第三批：让检索与记忆成为可控的模型输入

| 缺口 | 证据 | 增强方案 |
|---|---|---|
| 字符预算≠token预算 | Skills 5000字符、知识每片600、记忆无统一预算 | 统一prompt预算器；按来源与重要性裁剪，保留业务底线与最近消息 |
| 摘要无限追加 | memory L271 old+new | 新旧摘要再合并压缩，结构化保留未解决任务和用户事实 |
| 画像不是最新/聚合 | _get_profile仅limit1；按conv建多文档 | 用户聚合档+版本/来源，按时间更新并处理冲突和删除 |
| 知识ID只取前50字 | knowledge L88 | 完整内容哈希+doc_id/version/chunk_id；更新删除旧片并使缓存失效 |
| 长句超500与无overlap | _chunk_text L174–177 | 段落优先+硬上限+适度重叠；用长句、表格、代码块测试边界 |
| 1-dist含义不明确 | collection无显式距离度量 | 明确embedding与距离配置，返回distance及语义说明，阈值用数据校准 |
| 查询改写没有会话背景 | API只传req.message | 构造带明确对象的自包含查询；用“这个什么时候到”等追问测召回 |
| 业务资料相互矛盾 | troubleshooting自动退款 vs billing需核验 | 文档审核、时间/版本与优先级；裁判检查来源一致性 |

“是否用知识”也不应只看有没有返回文本。至少区分空召回、低相关、明确证据、降级说明。将文档看成不可信输入，不让其中嵌入的命令覆盖系统行为；真实工具权限必须独立于 prompt 执行。

## 第四批：补齐服务级评测和业务执行边界

建议将评测分层，而不是把所有东西塞进一个平均分：

1. **纯逻辑层**：意图投票、实体解析、路由门槛、缓存key、分片与熔断状态，用固定输入测确定性行为。
2. **依赖集成层**：Redis时序、Chroma导入检索、失败降级、并发压缩，以隔离测试数据验证状态一致性。
3. **完整用例层**：统一ChatService或HTTP入口，走RAG+记忆+路由+写入，检查状态、证据、跨轮实体与调用轨迹。
4. **模型质量层**：同一版本数据集，独立裁判/人工抽检，评估事实、来源忠实度、任务完成与拒答边界。
5. **运行层**：并发、超时、P50/P95、token/费用和降级率；区分冷缓存/热缓存、单Agent/多Agent。

基线应保存代码提交、模型ID、prompt/Skill版本、知识库版本、用例集哈希、样本量与时间；选定受保护基线而非每次无条件覆盖。修复分类标注粗细粒度差异后再比较历史指标。评测流量使用独立统计标签/实例，避免影响在线路由。

接入真实订单、退款、工单时，先增加可信身份和会话归属校验、工具schema完整验证、幂等键、审核/人工确认状态、执行后结果核验与审计记录。当前只有公开知识搜索，不能用“已经有工具框架”推导这些业务保障都已存在。

## 部署脚本的额外边界

- `build-image.sh build-test` 指向不存在的 test 阶段；`build` 默认选最后 development，production 必须显式指定。
- `run-image.sh --network` 帮助中存在，解析器却不处理；run-dev没有独立开发镜像或debugpy启动。
- `docker-deploy.sh` Redis健康/备份命令无密码；数据复制不是经过验证的一致性备份。
- Nginx仅HTTP，应用8000可直连，网关限流与metrics限制可以被绕过；Grafana/Alertmanager尚未部署。
- 模板开关和密码字段不等于实现对应认证、监控或调度能力；见[配置消费表](05_配置消费核对.md)。

## 面试如何讲改进优先级

可以这样说明：“我先保证请求状态正确——记忆顺序、不丢消息、降级标记准确；然后用统一入口和可靠埋点测质量与延迟；最后才决定是否需要更复杂的规划 Agent、多副本路由或真实 MCP 协议。每项改动都绑定一个输入案例和验收结果。”这体现的是工程取舍，而不是列待办名词。
