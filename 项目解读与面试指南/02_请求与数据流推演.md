# 一次请求如何经过整个系统

输入：一个用户消息与固定用户/会话标识。输出：回复、路由解释和存储副作用。本页用具体值推演源码，固定意图时会明确说明，不把推演写成模型实测。

## 场景一：退款咨询

```json
{
  "message": "订单号 AB12345，昨天支付了50元，我想退款",
  "user_id": "demo_user",
  "conv_id": "demo_refund_01"
}
```

第一站是 `api.main.ChatRequest`。message 必填，user_id 不传会变为 anonymous；conv_id 不传由 API 分配 UUID。如果下一轮忘记带回 conv_id，就会创建新会话，无法读取相同工作记忆列表。

第二站 `MemoryManager.get_context`：Redis 键为 `wm:demo_user:demo_refund_01`；会话摘要键为 `summary:demo_user:demo_refund_01`。情景记忆在 `episodic` 按 user_id 过滤后语义查询，画像从 `user_profile` 按 user_id 取一条。首次会话可能四项均为空；只要用户相同，也可能找到旧会话摘要/画像。

第三站 `recognize_intent`：API 从 recent_messages 取最后五**条**传 history，LLM 识别器进一步取最后三**条**。假设融合结果是 `refund`、分组 `billing`，正常紧急度 `LOW`。正则从本轮提取的结构为：

```json
{
  "order_id": ["AB12345"],
  "product": [],
  "date": ["昨天"],
  "amount": ["50元"],
  "error_code": ["AB12345"]
}
```

最后一个字段是代码真实边界：错误码正则也接受大写字母数字串，订单号会误入 error_code。日期保留“昨天”，没有标准化时间；产品字段一直为空。

第四站是 RAG。`refund` 属于业务类，因此调用 `search_with_rewrite`。默认先请求 LLM 改写三个角度，保留原问题，得到通常最多四个查询（代码没有严格限制模型返回数量）。每个查询调用 `knowledge_search`、各取至少五条；工具缓存可能减少实际库查询，但改写模型仍会调用。各路结果合并后用 LLM 给出索引顺序，取三条进入最终背景，每条内容截六百字符。

这些知识是退款**政策说明**，不是查询订单 AB12345 的真实支付记录。系统只注册知识搜索工具，没有订单查询或退款执行器。所以生成回复可以讲审核流程，不能声称已经为用户退款。

第五站 API 将记忆文本和知识文本拼成 `context`，再把上述实体和识别结果都填入 `Request`，调用 `Orchestrator.run`。因为 intent 已填，不会再调用识别模型。

固定 intent=refund 时，领域分数可计算为：

| 领域 | 计算 | 得分 |
|---|---|---:|
| billing | 意图 .75 + 支付/退款两个词 .36 + 金额 .15 | 1.26 |
| general | 基础 .1 + 订单词 .12 + 订单号 .1 | .32 |
| technical | 无技术意图/词；误抽 error_code +.2 | .2 |

主 Agent 选 billing；辅助必须不为 general，且同时达到 `.45` 与 `1.26×.55=.693`，所以没有辅助。对外 routing_confidence 被裁到 1.0，**不代表 100% 路由准确率**。实体误匹配在这个案例未改变最终决策，但在阈值附近可能造成影响。

第六站 `_best_agent(BILLING)`：当前池只有 `billing_0`，直接选它。`BaseAgent._build_system_prompt` 会匹配账单 Skill；正文与固定角色指令组合。记忆/知识作为 user 背景消息，实体作为另一个 user 消息，中间插入 assistant 确认句；最后再放实际用户消息，调用一次 LLM 生成文本。

第七站：`handle` 增加调用统计，检测回答是否含“转人工”等关键词。编排器返回 `OrchestratorResult`；API 依次保存用户消息与助手消息，然后调度画像任务，组装 `ChatResponse`。成功回复的准确措辞应是“说明了退款路径”，并非“完成了退款交易”。

## 场景二：下一轮只补一句话

```json
{"message":"多久能到账？","user_id":"demo_user","conv_id":"demo_refund_01"}
```

1. Redis 返回上一轮 user/assistant，两条都进入记忆 prompt。
2. 意图识别 LLM 看最近上下文，所以有机会理解为退款到账。
3. **实体仍然只抽本轮**：“多久能到账”不含订单号和金额，entities 不会自动继承上轮。生成模型可能从背景记住订单，但结构化路由没有跨轮槽位合并。
4. 知识检索收到原始短句，`search_with_rewrite` 未拿 history；即使意图识别利用历史得出了 refund，查询改写仍缺少明确订单/退款上下文。改进应在检索前构造自包含查询。
5. 两条新消息写入，累计达到 15 条时会压缩。这个阈值是消息条数，不能讲成 15 轮完整对话。

到这里应记住：对话的“连续性”有两套机制——给模型的自然语言历史、供规则使用的结构化状态。当前第一套存在，第二套没有完整跨轮合并。

## 场景三：复合问题为什么不一定并行

输入“登录一直 401，而且刚才还重复扣款了”，固定融合意图为 technical_login：

| 项目 | 分数/判断 |
|---|---|
| technical | .75 意图 + .18（401） + .2 错误码 = 1.13 |
| billing | .18（扣款） |
| general | .1 |
| 辅助最低分 | max(.45, 1.13×.55) = .6215 |
| 最终 | technical 单 Agent，billing .18 不达标 |

注意关键词表里的 `多扣` 不等于 `重复扣款` 子串，因此不能随意多加一份命中分。这个例子与原产品材料的“必然主辅协作”表述不同，已做离线验证。

一个能并行的固定意图案例是：“无法登录，重复扣款50元，申请退款并核对支付发票”，同样固定 technical_login。technical=.75+.18=.93；billing 命中多个关键词到封顶 .45，再加金额 .15，总 .6。辅助门槛为 .5115，账单 .6 达标，所以并行。

并行后两个 Agent **拿到同一条原问题与同一背景**，并非分别收到“只诊断登录”“只核验账单”子任务。输出用 `[technical - 主处理]`、`[billing - 辅助处理]` 拼接，没有综合模型判断是否重复、冲突或遗漏。真实 LLM 可能选择其他意图，因此上述固定结果用于讲公式，不用于保证所有线上回复。

## 场景四：失败发生在哪一层

| 失败位置 | 当前处理 | 用户侧/工程后果 |
|---|---|---|
| 识别模型失败 | failed=True，优先向量再关键词 | 仍可能有意图，但低质量向量也可能被接受 |
| 查询改写失败 | 使用原查询 | 检索可继续，召回角度减少 |
| 知识 handler 超时/异常 | 记失败、熔断、fallback | 能返回说明，但可能误标为用了知识 |
| 重排模型失败 | 返回原顺序前 k | reranked 仍可能 True |
| 专业 Agent 异常 | 尝试 GeneralAgent | actual agent 与 planned primary 不同 |
| 明确转人工/CRITICAL | escalation 目标无实例，回 General | escalated 只是标记，没有工单 |
| Redis 写入失败 | 多数调用没有捕获 | 模型已生成，HTTP 仍可能失败 |
| 画像模型失败 | 捕获并写日志 | 主回复通常不受影响；画像缺失 |

## 记忆压缩的顺序推演

平时 `LPUSH` 新消息到头，Redis 里是新→旧；读的时候 `reversed(raws)` 恢复旧→新。设待保留消息按时间是 11,12,13,14,15：

```text
keep                          = [11,12,13,14,15]   旧→新
for m in reversed(keep)       = [15,14,13,12,11]
逐条 LPUSH 后 Redis           = [11,12,13,14,15]   错：应该新→旧
读取再 reversed              = [15,14,13,12,11]   模型看到倒序
```

本次执行原 `_compress` 与原读取方法，用内存 Redis 和假摘要模型复现了这个结果。另一个独立风险是压缩期间的并发消息：读快照后等待 LLM，期间别人追加，最后 delete 重建会把追加丢掉。顺序修复与并发事务是两个不同问题，都需要处理。

## 一次请求到底多少次 LLM 调用

冷请求、业务意图、单 Agent、确实需要重排、未触发压缩时，通常是：识别 1 次 + 改写 1 次 + 重排 1 次 + 回答 1 次，**主链约 4 次**；后台画像再 1 次。重排候选不超过 k 时不调用裁判，识别缓存可减少 1 次；多 Agent 增加回答调用；失败降级和记忆压缩也可能增加调用。工具子查询通常查 Chroma，不是各调用一次回答 LLM。

向量计算与 messages.create 是不同成本项。代码未采集 usage/token/费用，不能从这一公式推算已经实测的成本。

主链延迟近似为：记忆读取 + 意图识别 + 改写 + 最慢子查询 + 重排 + Agent（并行取最慢，降级可串行）+ 记忆写入/可能压缩。`ChatResponse.latency_ms` 只拿编排器的一段时间，不能替代这个总和。

## 从推演得到的增强方向

统一调用入口；将历史变成自包含检索查询；将实体变成可更新且带来源的会话状态；为每一阶段记录 trace 和实际状态；用稳定文档 ID 和明确 degraded 标记连接检索与生成；用事务/版本锁保证压缩不丢消息。这些是从当前数据流直接推出的下一步设计，并非项目已有能力。
