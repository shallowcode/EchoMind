# EchoMind 项目面试口述与追问指南

> 根据本次对话中的面试讲解整理，整理日期：2026-09-24。
> 内容依据此前核对的项目代码与评测记录；个人贡献按实际负责范围表达。

你面试时最需要讲清楚的是：**用户一次提了好几个要求，你怎么确保每件事都被处理，而且系统说“办好了”时，真的有执行结果。**

这个项目可以围绕这一条主线讲，RAG、记忆、MCP 都放到它们解决的问题里，不用挨个背技术名词。

下面的回答可以直接拿来练口述。

## 1．面试官：“介绍一下你的项目。”

可以这样说：

> 这个项目是面向客服场景的多 Agent 系统，重点解决用户复合诉求容易遗漏的问题。
>
> 比如用户说：“登录报错了，帮我查一下订单，再申请退款。”系统既要回答排障问题，也要查询订单、提交退款申请。只生成一段看起来完整的回复，并不代表这些事情都办成了。
>
> 我的方案是把请求拆成显式子任务，交给不同角色的 Agent 处理，并记录每项任务的工具结果和完成状态。缺少结果就有限补做，最后逐项返回，避免遗漏。
>
> 同时，知识类问题通过 RAG 查依据，多轮对话通过记忆保留上下文；退款等操作由后端校验权限、金额和状态。
>
> 在 600 条参数化开发任务上，单 Agent 基线到增强方案的完成率从 67.67% 提升到 88%，其中复合任务从 56.67% 提升到 83.33%。

**说到这里就停。** 开场让面试官听懂问题、方案和结果，后面顺着追问展开。

## 2．面试官：“拿一个例子，说说完整流程。”

始终用同一个例子：

> “登录提示 401，帮我查询订单 ORD1001 的状态，再申请退款 20 元。”

你答：

> 首先读取当前会话，识别诉求和订单等信息，然后形成三个子任务：技术排障、订单查询、退款申请。
>
> 技术任务由技术 Agent 检索排障知识；订单和退款任务由账单角色分别处理。任务可以并发启动，各自需要的工具调用在任务内部完成，相同工具和参数的成功结果可以共享。
>
> 退款执行前，后端还要检查订单归属、用户是否明确要求退款、金额是否符合请求和可退余额。
>
> 最后按照三个任务分别回复：排障建议、查到的订单状态、退款申请的真实状态。某一项失败，也明确保留这一项，告诉用户尚未完成。

记住这条顺序就够了：

**读上下文 → 列任务 → 分别执行 → 检查证据 → 逐项回复。**

## 3．面试官：“为什么要多 Agent？一个 Agent 多写点提示词不行吗？”

> 一个 Agent 当然也能处理，所以我设置了单 Agent 基线。
>
> 拆分的价值是让每项诉求都有明确职责、工具范围和完成条件。例如技术任务只负责排障，不需要同时考虑退款流程；退款任务必须拿到申请结果，不能靠一句话就结束。
>
> 因此，我更看重任务覆盖和执行可检查，而不是单纯增加 Agent 数量。代价是更多模型调用、更高延迟，所以也不是所有简单问题都需要多个 Agent。

### 追问：“这些 Agent 是不同模型吗？”

> 当前复用同一个底层模型，通过不同角色、提示词、工具权限和独立执行上下文区分职责，不需要分别训练三个模型。

### 追问：“这不就是工作流吗？”

> 整体确实是受控工作流。程序负责拆分、权限和完成检查，Agent 在这个边界内理解问题、选择工具和组织回答。这种方式更适合流程明确的客服业务。

这两个回答比强调“自主智能协作”更贴近你的实现。

## 4．面试官：“任务是谁拆的？怎么保证不漏？”

> 当前支持的客服领域比较明确，所以拆分主要由业务规则结合识别出的实体完成，例如识别技术问题、订单查询、退款和人工诉求，生成任务清单。
>
> 每项任务记录负责人、必需工具、执行结果和缺失项。例如订单查询要有成功的查询结果，退款申请要有成功的申请结果。
>
> 如果 Agent 提前给了回答，但缺少必要证据，就在有限轮数内要求它补齐；仍然不满足就标记未完成。
>
> 最后按任务清单逐项输出，不再让模型自由合并一遍，减少合并时漏掉内容的风险。

这里最值得记住的是：

**“先把用户要做的事列出来，再逐项检查是否有完成依据。”**

边界也要能接住：

> 这能减少遗漏，但不能保证识别所有表达。规则没识别出的诉求，以及回答语义上的错误，仍可能漏检。

## 5．面试官：“上下文隔离和结果共享，不矛盾吗？”

> 两者解决不同问题。上下文隔离是减少无关任务的干扰；结果共享是减少重复工具调用。
>
> 例如技术任务会截取技术相关的请求片段，并去掉订单实体，限制它使用的工具，让它专注排障。
>
> 同一次请求中，如果两个任务调用了相同工具、参数也一致，就通过请求内的锁和共享结果复用成功响应。
>
> 当前属于任务输入和工具范围的隔离，历史记忆仍可能共用，并不是完全隔绝所有上下文。

别把“结果共享”说成“几个 Agent 不断互相聊天”。你的实现重点是**共享工具事实**。

## 6．面试官：“为什么做查询改写、并行召回和重排？”

> 用户的说法不一定和知识库一致。比如用户说“钱一直没回来”，文档可能写的是“退款到账时间”。
>
> 所以先保留原始问题，再生成不同表述，一起检索；把结果合并去重后，再让模型把更相关的内容排在前面。
>
> 查询改写是为了减少漏检，重排是为了减少无关内容进入回答。不同 Agent 复用同一套检索工具，避免各自实现一遍。
>
> 如果改写或重排失败，就退回原始查询或已有召回结果，并记录降级。

### 追问：“你怎么证明这几个步骤有效？”

> 当前主要验证的是整体方案效果，还没有把查询改写、重排分别做完整消融，所以不能给每一步单独归因。后续可以逐项关闭，对比检索质量和任务完成率。

## 7．面试官：“记忆、知识库、Skills 有什么区别？”

这题用三句话就能回答：

> 知识库保存业务依据，例如退款政策和排障文档。
>
> 记忆保存这个用户的上下文，例如之前提供的订单号、还没解决的问题；近期消息保留细节，较早历史用摘要压缩，画像保存语言和回复长度等偏好。
>
> Skills 保存角色处理业务的规则，例如退款要先确认信息、不能承诺已经到账，按角色注入提示词。

### 追问：“如何热更新？”

> 修改受管目录中的 Skill 文件后，通过管理员重载接口重新加载，让后续请求使用新规则，不需要修改 Agent 业务代码。

### 追问：“记忆是否可信？”

> 记忆用于理解上下文；订单和退款的当前状态仍然查业务工具，不能靠历史摘要认定已经退款。

## 8．面试官：“退款这么敏感，怎么避免模型乱操作？”

> 模型只负责提出工具调用，是否执行由后端判断。
>
> 首先，身份和租户来自登录凭证，不能由模型随意填写；其次检查订单归属，以及退款订单和金额是否符合用户明确提供的信息。
>
> 申请时在事务里检查可退余额，并把待审核金额计入占用额度，避免并发申请超额；同一操作重试通过幂等键返回已有结果，避免重复创建。
>
> Agent 只能提交待审核申请，审批和结算需要财务权限。目前完成的是沙箱账本闭环，没有真实资金转移。

三个容易追问的词，这样解释：

- **事务：** 查余额和创建申请作为一个整体处理，避免并发时都认为余额足够。
- **幂等：** 同一个操作重试，不重复产生业务记录；同一个键换了参数要拒绝。
- **状态机：** 申请、审批、结算按允许的顺序推进，不能跳过审批直接结算。

### 追问：“人工闭环怎么做？”

> 创建工单后，由客服接单、处理和关闭，解决说明写回原会话。这样用户后续继续问时，系统能看到处理结果。

## 9．面试官：“MCP 在里面起什么作用？超时熔断呢？”

> MCP 提供统一的工具访问入口，让兼容的客户端可以发现和调用订单、知识、退款、工单等工具。
>
> 当前 MCP 入口和聊天服务复用同一套业务工具层，权限和事务约束集中在业务层。聊天内部也可以直接调用这层，不是每次调用都必须经过 MCP 网络请求。
>
> 超时用于限制单次等待时间，熔断用于在工具连续故障后暂时停止调用，避免持续拖慢请求。未完成的任务会明确返回失败或降级状态。

这里不要说“MCP 保证安全”。**安全来自后端校验，MCP 负责接入。**

## 10．面试官：“你的完成率怎么测的？提升真的是多 Agent 带来的吗？”

这是最需要练熟的一题：

> 我做了两类评测。
>
> 一类是 1,200 条公开客服意图样本，覆盖 20 类源意图，映射到项目标签后，评估准确率、宏 F1 和混淆矩阵。这部分只测意图识别，不测退款有没有执行。
>
> 另一类是 600 条参数化业务开发任务，同一批任务分别运行单 Agent 和增强方案。完成判定结合工具执行记录、退款和工单的数据库状态，以及回答的必要检查。
>
> 整体完成率从 67.67% 到 88%，提升了 20.33 个百分点；150 条复合任务从 56.67% 到 83.33%，提升了约 26.67 个百分点。
>
> 但增强方案同时改变了任务编排和检索方式，所以这个结果证明的是整套方案的改善，不能全部归因于 Agent 数量。

> 数字说明：复合任务按原始通过数 85/150 和 125/150 计算，提升约 26.67 个百分点；直接用已四舍五入的 83.33% 减 56.67%，会得到 26.66 个百分点。

### 追问：“600 条怎么来的？”

> 来自 24 个模板族的参数化实例，通过替换订单、金额等生成，不是 600 个独立真实客服场景。目前是开发回归结果。

### 追问：“意图识别准确率多少？”

> 63.83%。这部分暴露了路由识别仍有不足。它和业务完成率使用不同数据、不同判定标准，不能把两个百分比直接比较。

### 追问：“88% 说明回答都正确吗？”

> 说明通过了当前自动检查。检查包含业务状态，也包含关键词规则，还不足以证明所有回答语义正确，需要独立人工标注集进一步验证。

### 追问：“12.78 秒是什么？”

> 是任务并发为 2 时，增强方案这次测试的 HTTP 请求 P95，表示约 95% 的请求耗时不超过这个值。它来自进程内 HTTP 测试环境，不能作为生产高并发表现。

### 追问：“效果提升有什么代价？”

> 请求 P95 从基线约 8.45 秒上升到 12.78 秒，模型费用估算也增加。后续可以让简单请求走短链路，把复杂编排主要用于复合诉求。

## 11．面试官：“你觉得最有价值的设计是什么？还有什么不足？”

这题可以收回你的主线：

> 我认为最有价值的是把任务完成从一句自然语言，变成有任务记录和工具证据的状态。
>
> 比如模型说“退款申请已提交”，必须能对应到真实申请结果；缺少结果就补做，仍然失败就说明未完成。最终逐项返回，也能减少复合诉求被遗漏。
>
> 当前不足主要是规则对复杂表达的覆盖有限，金额和部分退款表达仍有识别问题，自动评分也不能覆盖全部语义错误。下一步我会优先改进这些失败案例，并用独立人工标注数据验证。

不要承诺“彻底解决幻觉”。你的项目有约束和检查，但评测记录里仍保留了错误案例。

## 复习方法：先讲顺三个问题

现在复习时，只需要先脱稿讲顺三个问题：

1. **这个项目解决什么问题？**——复合诉求容易遗漏，回复和执行结果可能不一致。
2. **一条请求怎么走完？**——列任务、分工执行、查证据、补缺失、逐项返回。
3. **怎么证明有效？**——同一批业务任务做对照，看工具和账本结果，同时交代测试范围与代价。

每题先说结论，再拿“登录报错＋查订单＋退款”的例子解释。面试官追问哪一层，你再展开哪一层，不必一口气把整份简历讲完。
