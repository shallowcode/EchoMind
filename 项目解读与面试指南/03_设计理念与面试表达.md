# 如何解释设计，而不是复述功能名

输入：结构地图和已经读过的关键代码。输出：可在面试中展开、接受反问的设计论证。每个论证都按“问题→方案→代价→代码证据→改进验证”组织；不要把建议或模板包装成个人已完成业绩。

## 一分钟介绍的可靠版本

> 我研究的 EchoMind 是一个用 Python 和 FastAPI 实现的多角色客服编排项目。它把一次客服请求分成记忆读取、意图理解、按意图触发知识检索、角色路由和回答生成，再写回记忆。
>
> 我最关注三个设计：第一，意图、实体和紧急度统一成结构化请求，使检索和路由可以解释；第二，把知识检索与业务 SOP 分开，知识解决“依据什么回答”，Skills 解决“怎样处理”；第三，围绕模型调用补上缓存、超时、降级、监控和评测。
>
> 当前控制流主要是规则工作流，三类 Agent 共享模型调用实现。它还没有真实退款执行、人工工单或 MCP 协议服务。我能进一步解释路由门槛、记忆压缩和评测范围的限制，以及怎样验证改进。

如果你确实亲自实现了某个模块，可将相应部分改成“我实现了”。仅阅读、复现或修改小部分时，应说明真实范围。仓库中的 Java/Spring 简历版本不对应这里的源码，不要照搬。

## 为什么先识别意图，再生成回答

用户表述灵活，而工具/专业角色需要明确输入。意图识别将自然语言压缩为 refund、technical_login 等离散标签，同时保留粗组 billing/technical，使下游不用各自重新理解整句话。

源码用 LLM 理解上下文、向量匹配常见模板、关键词处理明确表达，最终固定权重投票。各路不是“互相证明正确”：LLM 会错，字符哈希对同义语义弱，关键词会忽略否定和顺序，固定权重也未经过校准。

三路开启时，同一 refund 获得 LLM=.8、embedding=.6、pattern=.5，融合贡献为 `.7×.8+.2×.6+.1×.5=.73`。若三路选择不同标签，是**分别给各自类别加分**，不是把三个置信度直接平均成一个通用可信度。配置 base_url 时是 `.85/.15` 两路。

面试追问“为什么 .7/.2/.1”：诚实回答这是代码里的启发式起点，没有训练/消融证据。下一步建立同一标注集，比 LLM-only、LLM+pattern、三路的 Accuracy、Macro-F1、拒答覆盖率、费用和耗时，再选权重；不能直接声称三路必然优于单路。

源码落点：[识别器](逐文件/core/intent_recognizer.py.md) 的 `recognize`、`_vote`、`_local_embedding`。记住：本地哈希是无需模型的词面近似，不能称为“训练过的语义向量模型”。

## 为什么区分领域选择和实例选择

“找技术专家还是账单专家”与“有三个技术专家时选哪个”是不同问题。`_domain_scores` 用业务信息选专业，`_best_agent` 才用调用成功率/平均延迟/monitor_penalty 选同类实例。

这样可以避免将快但不擅长账单的技术 Agent 选去处理退款。但代价是两套启发式参数，以及默认单实例下的效果有限。实例评分对累计历史敏感，没有探索流量，慢实例恢复后也未必获得足够新样本。

面试追问“你真的做了多 Agent 协作吗”：有主辅列表和并发执行，但目前是角色并行回答 + 文本拼接，没有任务分解、共享黑板、协商或结果仲裁。多 Agent 增加费用、延迟和冲突风险；简单问题单 Agent 更合适。是否并行应基于“一个回答确实会漏掉第二个独立子任务”，再用覆盖率和冲突率验证。

源码落点：[编排器](逐文件/agents/agent_orchestrator.py.md) 的 `_route_decision`、`run_parallel`、`_best_agent`。不要讲当前未使用的 `_route` 和 `_collaboration_targets` 是主入口。

## 知识、记忆、Skills 各解决什么

| 类型 | 内容与来源 | 解决的问题 | 主要失效方式 |
|---|---|---|---|
| Knowledge | 企业文档/政策，knowledge_base | 回答依据来自哪里 | 错误、过期、无权限或不相关材料 |
| Memory | 当前/历史用户会话与提炼画像 | “刚才那笔订单”指什么 | 顺序错乱、遗忘、画像混淆或泄露 |
| Skills | 运营写的 SOP，磁盘文件 | 应该按怎样的流程和边界回答 | 未匹配、截断、冲突、模型不遵循 |
| 固定 system prompt | General/Technical/Billing 角色 | 角色职责是什么 | 过于笼统、无法约束真实工具副作用 |

政策变动不该去改模型代码；会话信息不该写成所有用户共享的 Skill；真实权限校验也不该只是一段 prompt。当前把三种来源分开是好起点，但最终仍拼为文本，需要补充来源 ID、可信层级、token 预算和引用规则。

面试追问“有了 RAG 就不会幻觉吗”：检索解决访问资料，不保证资料正确或模型忠实。当前 demo 文档甚至含未证实认证/指标；应分别评估材料可信度、召回、排序、引用忠实度和回答正确性。

## 为什么查询改写和重排分两步

用户问“钱还没回来”，知识文档可能写“退款到账周期”。改写扩大表达覆盖，解决找不到候选；重排再按原问题排序，解决候选虽多却不相关。并行召回降低多个查询的串行等待，但不减少总计算量。

当前用 LLM 生成多角度查询，每路至少五条，最后用 LLM 返回索引列表。这会增加两次潜在模型调用，也可能改写偏离原意、证据去重失败、重排截断丢掉关键内容。应先用 Recall@k / MRR / nDCG 和最终答案指标判断收益，再考虑阈值触发改写、轻量 reranker 或缓存最终检索结果。这里的指标是建议实验，不是现有输出。

源码落点：[工具管理器](逐文件/mcp/tool_manager.py.md) 的 `search_with_rewrite`；[知识库](逐文件/mcp/knowledge_base.py.md) 的 `search`。按稳定 chunk_id 去重比哈希含分数字典更可靠。

## 为什么用 Redis 和 Chroma 两种存储

最近消息的主要需求是“按会话、有顺序、快速追加读取”，Redis List 合适；旧会话的主要需求是“找与当前问题相关的摘要”，向量检索合适。画像是提炼的长期偏好，当前也存 Chroma，但读取只是 user_id 精确过滤取一条，未实际做画像语义检索。

两种存储的代价是跨存储一致性：旧消息摘要归档失败时是否还能删除 Redis 原消息？当前答案是可能继续删。压缩同时遇到新消息怎样避免丢失？当前无事务。工程增强应先定义持久化完成条件和重试队列，再讨论更复杂的“记忆智能”。

源码落点：[记忆管理](逐文件/memory/conversation_memory.py.md)。应能解释 LPUSH 与读取反转，以及为什么 `reversed(keep)` 是 bug。

## async 到底改善了什么

协程在等待网络时把控制权让给其他请求，适合模型和 Redis I/O；同步 Chroma 操作用 `to_thread` 放到线程，避免直接堵住事件循环。`gather` 并发等待多个调用，不代表 CPU 密集计算自动多核。

“async def”本身不保证所有内部代码非阻塞：Chroma 构造/默认导入、Skills 重载和 CLI input 仍有同步工作。也不保证并发安全：共享 Redis 读改写、统计和画像更新都可能存在竞争。应把异步吞吐、截止时间、背压、任务回收和一致性分别设计。

## 缓存、超时、熔断、降级分别保护什么

| 机制 | 核心问题 | 本仓库现状 |
|---|---|---|
| 缓存 | 相同调用避免重复工作 | 工具 TTL 字典；识别字典无 TTL、非严格 LRU |
| 超时 | 不让一个依赖无限占用等待 | 工具 handler 有 wait_for；整个检索/Agent 无统一 deadline |
| 熔断 | 已知依赖坏了，暂时不再持续打它 | 三态存在；半开单探测未实现 |
| 降级 | 失败时仍给可理解结果 | 知识 fallback、专业 Agent 转 General |

“可返回”不等于“成功完成任务”。生产状态应区分 completed、degraded、failed、needs_human，并保留 error 和实际执行者。重试只能在幂等和明确预算下使用；将来新增退款等写工具，需要幂等键、授权、审核、结果确认，不能套当前读缓存直接执行资金动作。

## 如何把评测说清楚

分类有标准答案，因此可以算 Accuracy 与每类 Precision/Recall/F1；Macro-F1 对每类等权，便于发现少数类别被整体准确率掩盖。比如某类 TP=8、FP=2、FN=4，P=.8、R=2/3、F1≈.727。当前标签集取真实标签与预测标签并集。

对话没有固定唯一文字答案，所以用 LLM Judge 的 relevance、accuracy、completeness、helpfulness 四维平均，阈值 .75。问题在于裁判没有业务事实证据，用它测“正确性”只能算主观估计。后续需将来源文档、期望任务状态、人工标注一致性纳入评测。

当前对话评测不经过完整 `/chat`，因此无法测 RAG/真实记忆/HTTP 状态。基线每次覆盖且无版本元数据。正确介绍是“实现了分类评测、编排器级多轮回答评分与相对回归提示”，不要称已有完整生产端到端质量门禁。

## 五分钟展开顺序

1. **业务目标**：用户会跨轮补信息、同句混多个问题，需要可解释分流和可靠知识依据。
2. **主链路**：从 `/chat` 到两种记忆、意图、RAG、Request、Agent、写回。
3. **一个设计深挖**：现场计算领域分数，或演示缓存/熔断状态机，或解释记忆压缩时序。
4. **效果怎么证明**：明确当前仅有历史小样本和隔离行为验证，提出同数据集消融、完整 HTTP 轨迹测试与延迟分段统计。
5. **下一步**：先修状态一致性和边界，再引入真实工具与更复杂规划。

## 常见反问与可核对答案

| 追问 | 回答要点 |
|---|---|
| 为什么不用 LangGraph？ | 当前流程有限，用 Python 直接表达易读；引入图状态机应基于持久化执行、分支恢复、人工审批需要。当前并未使用该框架。 |
| MCP 在哪？ | `mcp/` 目录是本地工具治理，实现 handler 注册调用；没有协议服务。接协议需补适配层和会话/传输。 |
| 转人工后谁收到消息？ | 当前无人收到，只有返回标记/日志；待接工单系统。 |
| 用户间安全隔离怎么保证？ | 仅有 user_id 过滤和会话键，没有认证绑定，客户端可伪造 user_id；不能声称可靠隔离。 |
| 监控如何提高回答质量？ | 当前反馈的是调用成功和延迟，不直接看答案质量；每类单实例，降权效果有限。 |
| 多轮实体记住了吗？ | 自然语言背景保留，结构化实体只抽本轮且其他入口未填；需补槽位状态。 |
| 延迟和成本是多少？ | 当前无可复验全链压测与 token 费用数据；只能给模型调用次数和阶段计时方案。 |
| 热加载更新所有服务了吗？ | 当前更新一个进程的内存管理器；多进程需版本广播与原子切换。 |

## 这套表达还需要你补什么

挑一个你真正理解并亲自验证的改进，保存输入、失败输出、修复和验证证据，才能从“能读懂别人的项目”进到“有工程实践可讲”。优先选择记忆压缩顺序、检索稳定 ID 去重或评测统一入口，避免一次堆进多个框架而没有可验证结果。
