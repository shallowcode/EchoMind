# 项目核心事实

## A01｜项目到底解决什么问题
检索词：项目介绍、做什么、业务价值、EchoMind、SupportFlow。性质：当前实现。

**简短讲法：** EchoMind 当前运行的是 SupportFlow v2，一个 Python/FastAPI 客服后端：把用户问题转成知识查询、订单查询、退款申请或人工工单，并用工具结果和业务记录核对处理状态。

**展开要点：**

- 自然语言入口负责理解和解释；业务程序负责身份、权限、金额、状态流转。
- 一条消息可以拆成技术、订单、退款、人工等多个子任务。
- 主要入口是 HTTP、MCP 和命令行；现有材料无法确认完整产品的生产上线情况。

**边界：** 不能从代码推出真实客户数、节省人力、线上营收或本人独立开发经历。

**依据：** `api/main.py:1`；`supportflow/api.py:70`（create_app）；`supportflow/planning.py:86`（plan_tasks）

## A02｜一条请求的完整路径
检索词：主链路、请求流程、架构、端到端。性质：当前实现。

**简短讲法：** 请求先鉴权和查重，再读取会话、识别意图、拆任务；Agent 调用受控工具，系统检查证据后逐项回复，最后保存会话和追踪记录。

**展开要点：**

- 顺序：Token → 请求指纹/重放 → 并发限制与会话租约 → 历史/摘要/实体 → 意图和任务规划 → Agent/工具 → 结果检查 → 持久化。
- 不同子任务可以并行；同一个会话的写入通过租约保护。
- Redis 和 Chroma 的会话投影发生在 SQL 核心提交之后，投影失败会记录降级。

**边界：** 工具业务事务和整轮对话事务分开；不能说整个请求中途失败会把所有业务操作一起回滚。

**依据：** `supportflow/service.py:325`（ChatService.chat）；`supportflow/service.py:426`（ChatService._run）；`supportflow/store.py:356`（Store.commit_turn）

## A03｜多 Agent 指什么
检索词：Agent、多智能体、多个模型、角色分工。性质：当前实现。

**简短讲法：** 这里的多 Agent 是同一个模型按任务使用不同角色、上下文和工具权限，不是训练了多个独立模型。价值在职责拆分和完成情况检查。

**展开要点：**

- 技术任务只做排障检索；账单任务处理订单和退款；人工任务创建工单。
- 每个子任务有自己的证据、答复、尝试次数和完成状态。
- 最终答复由程序逐项呈现，不再让另一个模型自由改写。

**边界：** 这是规则驱动的任务编排，不是智能体自由协商，也没有训练或微调证据。

**依据：** `supportflow/service.py:33`（ToolAgent._call_llm）；`supportflow/service.py:426`（ChatService._run）；`supportflow/planning.py:20`（Subtask）；`supportflow/planning.py:164`（render_tasks）

## A04｜知识、记忆、Skill 分别是什么
检索词：知识库、RAG、Memory、Skill、SOP、上下文。性质：当前实现。

**简短讲法：** 知识库提供政策和排障依据，记忆保留这个用户之前说过什么，Skill 提供业务处理步骤。三者作用不同，权限和资金限制仍由代码执行。

**展开要点：**

- Knowledge：按租户检索知识片段；Memory：历史、摘要、订单实体和用户偏好。
- Skill：从文件加载的业务 SOP，根据关键词和角色匹配后进入提示词。
- 例如退款政策属于知识，上一轮订单号属于记忆，先确认信息再说明待审核属于 SOP。

**边界：** Skill 写了某项业务，不代表已经有对应工具；提示词不是权限边界。

**依据：** `supportflow/knowledge.py:165`（Knowledge.retrieve）；`supportflow/service.py:426`（ChatService._run）；`core/skill_loader.py:1`

## A05｜模型如何调用业务工具
检索词：工具调用、function calling、JSON、参数校验。性质：当前实现。

**简短讲法：** 模型输出结构化 JSON，列出答复或工具调用；程序验证格式、工具权限和参数，再执行真实业务逻辑，把结果交回模型。

**展开要点：**

- AgentTurn 包含 answer 和 tool_calls，一次最多 3 个调用。
- 工具包括 knowledge_search、order_lookup、refund_request、ticket_create、ticket_status。
- 默认工具轮数为 3，另有最后一次只允许回答的生成机会；格式修复也消耗同一预算。
- 支持 JSON Schema 的后端使用结构约束，否则依靠提示词与解析校验；程序不会仅凭模型文字就执行付款。

**边界：** 项目没有统一使用各家供应商原生 function calling 协议。轮数有上限也不保证模型一定完成任务。

**依据：** `supportflow/contracts.py:50`（AgentTurn）；`supportflow/service.py:33`（ToolAgent._call_llm）；`supportflow/tools.py:105`（Tools.call）；`supportflow/model.py:26`（Model.complete）

## A06｜身份、租户与角色
检索词：权限、多租户、鉴权、Token、RBAC。性质：当前实现。

**简短讲法：** Token 在服务端解析为租户、用户和角色；数据查询与写入依据这个身份检查归属，模型自己输出的身份不算授权。

**展开要点：**

- 数据库保存 Token 的 SHA-256 哈希，支持过期和撤销。
- 退款申请限定本人订单；财务审核和结算还要求申请人与操作人不同。
- 知识按租户隔离，会话和个人数据还需要用户归属检查。

**边界：** 不是完整企业 SSO/OIDC 系统；角色检查并不代替每个业务对象的归属检查。

**依据：** `supportflow/store.py:68`（Store.issue_token）；`supportflow/store.py:83`（Store.authenticate）；`supportflow/store.py:121`（Store.refund_request）；`supportflow/store.py:174`（Store.approve_refund）；`supportflow/contracts.py:15`（Principal）

## A07｜外部模型和 MCP 接入
检索词：MCP、外接模型、模型适配、OpenAI compatible、Anthropic。性质：当前实现。

**简短讲法：** 模型适配层负责调用模型生成内容；MCP 层负责让外部客户端发现并调用本项目工具。两条接入链路解决不同问题。

**展开要点：**

- Model 支持 compatible 和 anthropic 两类 HTTP 适配，使用配置中的模型名与地址。
- MCP 使用官方 SDK FastMCP，挂载 /mcp/，暴露 5 项业务工具并验证 Token。
- 外部 MCP 调用不经过聊天任务拆分；退款工具的结构化调用直接表示申请意图，数据库仍检查归属、金额和状态。

**边界：** 没有自动训练外接模型；也没有因为接入 MCP 就获得财务审批或付款工具。

**依据：** `supportflow/model.py:26`（Model.complete）；`supportflow/protocol.py:31`（build_mcp）

检索词：旧版、版本区别、Java、Spring、旧文档、入口。性质：当前实现。

**简短讲法：** 介绍当前项目应以 api/main.py 指向的 supportflow 为准。仓库同时保留旧路由、旧记忆和旧评测，旧文档中的结论不能直接套到 v2。

**展开要点：**

- Java/Spring 简历包装与这个 Python 源码不一致，不能当作当前技术栈。

**边界：** 不要删除历史材料来假装项目没有演进；检索时标明 current-v2 与 legacy，默认只检索当前版本。

# 核心问题与解决

## P01｜复合问题容易漏掉一个诉求
检索词：难点、遇到什么问题、漏答、复合任务、任务拆分。性质：当前实现＋历史记录。

**简短讲法：** 最核心的问题是用户一句话里有多件事，模型容易只回答其中一件。项目把诉求拆成独立任务，每项写明必须取得的工具证据，最后逐项呈现，减少遗漏。

**展开要点：**

- 例：登录失败，同时查订单并申请退款。技术、订单、退款分别处理，不能用一段排障建议代替整条请求。
- Subtask 保存职责、required_tools、observations、missing 和 status。没有证据就要求补齐；预算耗尽保留未完成状态。
- 2026-09-09 历史开发评测复核中，150 条复合任务完成率从 56.67% 到 83.33%。

**边界：** 这组差异包含规划、检索等多项变化，不能把提升全部归因于并行；规则也无法覆盖所有自然语言表达。

**依据：** `supportflow/planning.py:86`（plan_tasks）；`supportflow/planning.py:33`（Subtask.gaps）；`supportflow/planning.py:164`（render_tasks）；`评测结果/GLM-1200复核/audit.json:1`；`评测结果/GLM-1200复核/README.md:1`

## P02｜回答成功不等于业务执行成功
检索词：幻觉、虚假成功、工具证据、任务完成、申请已提交。性质：当前实现。

**简短讲法：** 第二个问题是模型可能说“已经处理”，实际没有工具结果。项目把完成条件放到程序里，用成功工具记录、知识来源和业务状态判断，缺失就继续修复或标记未完成。

**展开要点：**

- 退款任务要求成功的 refund_request；技术任务要求有效知识来源和具体排查建议。
- 最终渲染保留每项结果与缺口，不再通过一次自由总结掩盖失败。
- 完整评测还查数据库中的退款金额、申请数和状态，不只匹配答复文字。

**边界：** 目前部分答复检查仍是关键词规则，历史复核也记录过没有申请却声称提交的问题；不能说已彻底消除幻觉。

**依据：** `supportflow/planning.py:33`（Subtask.gaps）；`supportflow/service.py:33`（ToolAgent._call_llm）；`evaluation/full_chain.py:47`（verify）；`评测结果/GLM-1200复核/audit.json:1`；`评测结果/GLM-1200复核/README.md:1`

## P03｜重试和并发可能造成重复退款
检索词：幂等、重试、重复退款、超额退款、并发写入。性质：当前实现。

**简短讲法：** 资金类操作不能靠模型自觉。项目用幂等键处理重复请求，用事务预占待处理退款金额，并把申请、审核和结算分开。

**展开要点：**

- 聊天请求：同 request_id 和同指纹返回已保存结果；同 ID 换内容会冲突。
- 退款写入：同租户、用户、幂等键复用原申请；同键改金额、订单或原因会拒绝。
- 可退额度 = 总额 − 已结算退款 − pending/approved/processing 预占金额；检查和新申请在同一事务。
- 财务审批和结算不能由申请人自己完成。

**边界：** 幂等只在约定键和载荷范围内成立，不是任何文本重复都自动识别；也不是分布式全局 exactly-once 承诺。

**依据：** `supportflow/service.py:325`（ChatService.chat）；`supportflow/store.py:346`（Store.cached_request）；`supportflow/store.py:121`（Store.refund_request）；`supportflow/store.py:174`（Store.approve_refund）；`supportflow/store.py:40`（Store.tx）

## P04｜金额和错误码容易混淆
检索词：500元、错误码、金额抽取、部分退款、语义绑定。性质：当前实现。

**简短讲法：** 数字不能只按字面匹配。任务规划要求 4xx/5xx 具有报错上下文，避免把 500 元直接当成技术故障；退款金额还必须来自用户原始请求。

**展开要点：**

- 聊天退款调用把“数字 + 元”用 Decimal 换成分，再核对模型给出的 amount_cents 和已知订单号。
- 明确申请与否定表达分别检查，不能从“不要退款”生成退款操作。
- 当前能检查金额是否出现，却不能完全证明它属于哪一笔订单。

**边界：** “订单 500 元，只退 100 元”有多个金额时仍有语义绑定风险；这属于待改进点，不是已经彻底解决的问题。

**依据：** `supportflow/planning.py:86`（plan_tasks）；`supportflow/planning.py:12`（TECHNICAL_PATTERN =）；`supportflow/service.py:33`（ToolAgent._call_llm）；`supportflow/service.py:426`（ChatService._run）；`评测结果/GLM-1200复核/audit.json:1`；`评测结果/GLM-1200复核/README.md:1`

## P05｜Agent 越界处理或重复写入
检索词：职责污染、工具权限、重复工单、共享结果。性质：当前实现。

**简短讲法：** 多个 Agent 同时处理时，可能抢做同一件事。项目给子任务限定工具范围，并在同一请求内共享成功调用结果，减少越界和重复执行。

**展开要点：**

- 技术子任务只允许 knowledge_search，当前消息也会裁剪为技术相关片段。
- 相同工具名和参数使用共享锁；已有成功结果直接复用。
- 退款原因、工单摘要来自原始请求的稳定截取，避免不同 Agent 改写后形成不同载荷；数据库再做幂等兜底。

**边界：** 技术上下文中的历史仍可能包含其他业务内容；共享结果只覆盖同一次请求，失败调用不会被当成成功缓存。

**依据：** `supportflow/planning.py:76`（Subtask.allowed_tools）；`supportflow/planning.py:177`（scope_message）；`supportflow/service.py:231`（ToolAgent._execute_tool）

## P06｜多轮会话会遗忘或写乱
检索词：记忆、上下文丢失、摘要、Redis、会话并发。性质：当前实现。

**简短讲法：** 多轮对话需要保留订单号和未完成事项，也要防止两轮请求互相覆盖。项目用 SQL 保存会话状态和历史，用会话租约保护写入，再叠加摘要和可选检索记忆。

**展开要点：**

- 本轮非空实体合并到会话状态，因此下一轮可以继续使用已提供订单号。
- 模型上下文包含摘要、最近 8 条消息、用户偏好，以及可选 Chroma 召回。
- Redis 内容必须与 SQL 的轮次和消息一致才被采用；核心数据已提交后才写投影。

**边界：** 当前仍先读取 SQL 再比较 Redis，不能声称已靠缓存消除数据库查询；摘要是有损压缩。

**依据：** `supportflow/service.py:426`（ChatService._run）；`supportflow/service.py:325`（ChatService.chat）；`supportflow/store.py:306`（Store.acquire_conversation）；`supportflow/store.py:356`（Store.commit_turn）

## P07｜用户说法与文档表达不同
检索词：召回、改写、重排、RAG优化、知识查不到。性质：当前实现。

**简短讲法：** 用户说“钱没回来”，文档可能写“退款到账周期”。增强检索保留原问题并生成最多两个改写，分别召回、按片段 ID 去重，再按原问题重排。

**展开要点：**

- 每路召回至少 5 条；候选超过返回数时才尝试模型重排，默认最终返回 3 条。
- 改写失败保留原始查询；重排失败保留已有候选顺序，并标记降级。
- SQL 后端是词面匹配，Chroma 后端才是向量检索，讲解时要区分配置。

**边界：** 没有单独消融数据证明改写或重排贡献了多少；底层搜索本身不可用时，改写降级也不能让知识凭空出现。

**依据：** `supportflow/knowledge.py:125`（Knowledge.search）；`supportflow/knowledge.py:165`（Knowledge.retrieve）

## P08｜知识更新后读到旧内容
检索词：知识版本、缓存失效、双写一致性、脏数据。性质：当前实现。

**简短讲法：** 知识内容变更后，旧缓存可能继续影响回答。项目按内容生成版本，知识检索缓存带上租户版本，向量结果还要经过 SQL 有效片段检查。

**展开要点：**

- 文档按 500 字符分块、步长 420；片段 ID 包含文档版本和位置。
- 缓存键包含租户、用户、角色、查询、检索模式和知识版本，TTL 为 300 秒。
- Chroma 返回后过滤 SQL 中已失效的片段 ID，降低旧向量残留影响。

**边界：** SQL 与 Chroma 双写不是一个原子事务；过滤旧片段不能保证新片段已可检索。仅改标题也不会改变内容版本。

**依据：** `supportflow/knowledge.py:58`（Knowledge.add）；`supportflow/knowledge.py:118`（Knowledge.version）；`supportflow/knowledge.py:125`（Knowledge.search）；`supportflow/tools.py:105`（Tools.call）

## P09｜外部依赖失败拖住请求
检索词：超时、熔断、降级、限流、稳定性。性质：当前实现。

**简短讲法：** 模型和检索都是可能慢或失败的依赖。项目限制同时处理数量和总时长，对工具设置超时与熔断，并把失败记录到追踪信息里。

**展开要点：**

- 默认最多 4 个在途聊天请求，总超时 180 秒；模型超时 90 秒。
- 知识工具超时 90 秒，其他工具 10 秒；熔断按租户和工具隔离，失败计数达到 3 后打开，冷却 10 秒，半开只允许一个探测。
- 权限错误、参数错误不当作后端故障累计；附属存储失败可使结果标记 degraded。

## D02｜为什么 SQL 做事实来源
检索词：SQLite、数据库选型、Redis、Chroma、一致性。性质：依据代码的设计解释。

**简短讲法：** 订单、退款和会话需要明确状态与事务，所以由 SQL 保存事实；Redis 提供可选缓存，Chroma 提供可选语义检索。缓存和向量库失败不应抹掉核心业务记录。

**展开要点：**

- 取舍是 SQLite 写并发有限，跨 SQL/Chroma 仍有一致性窗口。

**边界：** 不能宣称已经验证高并发分布式部署；迁移数据库、持久化重试投影属于后续方案。

## S05｜项目能力边界速查
检索词：别说错、不支持、上线、生产、训练模型。性质：当前实现。

**简短讲法：** 可以讲已经实现的后端能力和历史开发实验；不能把沙箱、模拟测试、提示词约定或后续建议说成真实生产业绩。

**展开要点：**

- 退款申请 ≠ 审批通过 ≠ 资金到账；知识建议 ≠ 故障已修复；工单已创建 ≠ 人工已解决。
- MCP 接口实现 ≠ 企业 SSO；SQLite 并发保护 ≠ 已验证大规模分布式系统。
- Chroma 检索 ≠ 自研向量模型；多角色调用 ≠ 训练多个模型；模型 JSON 调用 ≠ 统一供应商原生 function calling。
- 发票规则检索 ≠ 已接自动开票；Docker 文件存在 ≠ 镜像已构建并部署成功。

**边界：** 没有资料时直接说“现有材料没有证据”，不要用听起来合理的数字补空白。

**依据：** `supportflow/contracts.py:63`（Settings）；`supportflow/planning.py:86`（plan_tasks）；`supportflow/protocol.py:31`（build_mcp）；`supportflow/service.py:33`（ToolAgent._call_llm）

## S06｜项目事实不能自动变成本人经历
检索词：个人贡献、我负责什么、团队、开发周期、本人实现。性质：待本人确认。

**简短讲法：** 源码能证明项目有什么，不能证明你独立完成了什么。个人职责、时间、团队和实际改动，应来自你补充并确认的经历记录。

**展开要点：**

- 当前尚未核实：任职单位、团队规模、项目周期、本人负责模块、亲手排查的故障、上线范围和业务收益。
- 讨论实现机制可以用“项目采用了”；确认实际贡献后，再将对应条目写成“我实现了/我排查了”。
- 只读过、复现过或参与修改过，应分别说明，不要统一写成独立负责。

**边界：** 外接模型不得自行把这里的任何项目功能或历史实验全部归到用户个人名下。

**依据：** `项目解读与面试指南/03_设计理念与面试表达.md:13`（如果你确实亲自实现）
