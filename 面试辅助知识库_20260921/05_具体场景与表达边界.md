# 具体场景与表达边界

适用项目：EchoMind / SupportFlow v2。整理日期：2026-09-21。项目事实不自动代表个人贡献。

## S01｜用一笔退款解释额度预占
检索词：退款例子、事务例子、状态机、钱怎么保证。性质：依据实现构造的例子。

**简短讲法：** 假设订单 500 元，已经退了 100 元，又有 200 元申请待审核，可用额度就是 200 元。再申请 250 元应被拒绝，申请 150 元则可进入待审核。

**展开要点：**

- 代码用分存储：总额 50000，已退 10000，预占 20000，可用 20000。
- 新申请 15000 分后，可用额度为 5000 分；审批通过仍占额度。
- 结算后这 15000 分从预占转为已退款，不能再扣一次；拒绝则释放相应预占。

**边界：** 这是依据代码构造的讲解例子，不是一次真实用户交易或已执行的新测试；实际结算还需权限和合法状态。

**依据：** `supportflow/store.py:121`（Store.refund_request）；`supportflow/store.py:174`（Store.approve_refund）；`supportflow/store.py:191`（Store.settle_refund）

## S02｜用一句复合请求讲清编排
检索词：完整例子、登录失败并退款、流程推演。性质：依据实现构造的例子。

**简短讲法：** 示例：“登录报错 500，查一下订单 ORD101401 的状态，并帮我申请退 100 元。”在已识别订单且授权成立时，会规划技术排障、订单查询和退款申请三个任务。

**展开要点：**

- 技术任务检索排障知识并给步骤，不承诺故障已经修复。
- 订单任务读取真实订单；退款任务校验归属与额度后创建 pending 申请。
- 最后按三项输出；若退款失败，仍保留技术与订单的结果，并说明退款未完成。

**边界：** 是否成功还依赖输入识别、模型调用、权限和数据库状态；申请成功不等于退款到账。这个例子是流程推演，不是新增跑分证据。

**依据：** `supportflow/planning.py:86`（plan_tasks）；`supportflow/planning.py:177`（scope_message）；`supportflow/planning.py:164`（render_tasks）；`supportflow/store.py:121`（Store.refund_request）

## S03｜退款已写入但回答失败怎么办
检索词：异常恢复、超时重试、事务边界、请求重放。性质：依据实现的流程分析。

**简短讲法：** 工具写入成功后，后续模型回答仍可能失败。重试时应复用原请求 ID，让退款幂等键找回已有申请，而不是默认“没收到回答就什么也没发生”。

**展开要点：**

- 如果整轮已提交，聊天请求可直接重放保存的响应。
- 如果只有退款工具已提交，同键同载荷的退款调用返回原申请，避免重复创建。
- 请求内共享锁与数据库幂等分别覆盖同轮并发和后续重试。

**边界：** 不能说超时必然回滚业务操作；改变请求 ID 或业务载荷不等于相同重试，必须查询真实状态。

**依据：** `supportflow/service.py:325`（ChatService.chat）；`supportflow/service.py:231`（ToolAgent._execute_tool）；`supportflow/store.py:121`（Store.refund_request）

## S04｜人工工单完成到什么程度
检索词：转人工、工单状态、人工接管、客服闭环。性质：当前实现。

**简短讲法：** 转人工会创建真实工单，客服可以接单、解决和关闭；解决信息会写回关联会话。创建工单表示进入处理流程，不表示人工已回复或问题已解决。

**展开要点：**

- 状态顺序为 open → assigned → resolved → closed。
- 更新需要正确版本号；解决需要处理人或管理员权限以及解决内容。
- 当前是后端流程与接口，没有完整客服坐席界面或实时人工通知系统。

**边界：** 工单 assignee 不是一个已经实现完整员工目录验证的账号体系。

**依据：** `supportflow/store.py:221`（Store.create_ticket）；`supportflow/store.py:258`（Store.update_ticket）

## S05｜项目能力边界速查
检索词：别说错、不支持、上线、生产、训练模型。性质：当前实现。

**简短讲法：** 可以讲已经实现的后端能力和历史开发实验；不能把沙箱、模拟测试、提示词约定或后续建议说成真实生产业绩。

**展开要点：**

- 退款申请 ≠ 审批通过 ≠ 资金到账；知识建议 ≠ 故障已修复；工单已创建 ≠ 人工已解决。
- MCP 接口实现 ≠ 企业 SSO；SQLite 并发保护 ≠ 已验证大规模分布式系统。
- Chroma 检索 ≠ 自研向量模型；多角色调用 ≠ 训练多个模型；模型 JSON 调用 ≠ 统一供应商原生 function calling。
- 发票规则检索 ≠ 已接自动开票；Docker 文件存在 ≠ 镜像已构建并部署成功。

**边界：** 没有资料时直接说“现有材料没有证据”，不要用听起来合理的数字补空白。

**依据：** `supportflow/contracts.py:63`（Settings）；`supportflow/planning.py:86`（plan_tasks）；`supportflow/protocol.py:31`（build_mcp）；`supportflow/service.py:33`（ToolAgent._call_llm）

## S06｜项目事实不能自动变成本人经历
检索词：个人贡献、我负责什么、团队、开发周期、本人实现。性质：待本人确认。

**简短讲法：** 源码能证明项目有什么，不能证明你独立完成了什么。个人职责、时间、团队和实际改动，应来自你补充并确认的经历记录。

**展开要点：**

- 当前尚未核实：任职单位、团队规模、项目周期、本人负责模块、亲手排查的故障、上线范围和业务收益。
- 讨论实现机制可以用“项目采用了”；确认实际贡献后，再将对应条目写成“我实现了/我排查了”。
- 只读过、复现过或参与修改过，应分别说明，不要统一写成独立负责。

**边界：** 外接模型不得自行把这里的任何项目功能或历史实验全部归到用户个人名下。

**依据：** `项目解读与面试指南/03_设计理念与面试表达.md:13`（如果你确实亲自实现）
